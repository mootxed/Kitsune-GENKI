# Внутренний регламент обработки уязвимостей (Security Response Guide)

Данный документ описывает внутренний порядок действий сопровождающих (maintainers) проекта KotoKitsu при получении отчёта о потенциальной уязвимости.

---

## Чек-лист обработки уязвимости (Security Advisory Checklist)

1. **Подтвердить получение**: В течение 3 рабочих дней отправьте подтверждение исследователю через GitHub Private Vulnerability Reporting или приватный канал.
2. **Изолировать секреты**: Убедитесь, что отчёт, эксплоиты, токены и приватная информация не скопированы в публичные Issues, Discussions, коммиты или ветки.
3. **Воспроизвести проблему**: Создайте локальный тестовый стенд на изолированной копии приложения и проверьте воспроизводимость уязвимости.
4. **Определить затронутые версии**: Проверьте текущий `main`, последний alpha-релиз и поддерживаемые компоненты.
5. **Назначить уровень серьёзности (Severity)**: Оцените риски по модели классификации (см. ниже).
6. **Подготовить приватный патч**: Создайте приватную ветку или GitHub Security Advisory draft для разработки исправления.
7. **Добавить регрессионный тест**: Напишите автоматизированный тест в `tests/security/`, проверяющий уязвимость на нейтральном payload.
8. **Разработать исправление**: Реализуйте исправление с минимальным затрагиванием смежного кода.
9. **Проверить сохранность данных**: Убедитесь, что патч не ломает существующий прогресс пользователей, IndexedDB и миграции State.
10. **Выпустить новую версию**: Соберите и опубликуйте патч-версию приложения для поддерживаемых веток.
11. **Опубликовать Security Advisory**: Заполните публичный GitHub Security Advisory с описанием проблемы и указанием исправленной версии.
12. **Благодарность исследователю**: Укажите имя/псевдоним исследователя в благодарностях (по согласованию).
13. **Согласовать публичное раскрытие**: Согласуйте с исследователем дату и формат детальной публикации (Coordinated Disclosure).

---

## Модель классификации уязвимостей (Severity Model)

Классификация уязвимостей KotoKitsu учитывает специфику оффлайн-ориентированного PWA без собственного бэкенда.

### Critical (Критический уровень)

- Выполнение произвольного JavaScript-кода (Stored XSS без специфических действий) в контексте origin KotoKitsu.
- Массовая утечка локально сохранённых API-ключей OpenRouter.
- Удалённое повреждение или сброс учебного прогресса без явного действия пользователя.
- Supply-chain компрометация опубликованной сборки приложения.

### High (Высокий уровень)

- Stored XSS, требующий однократного действия пользователя (например, импорт файла бэкапа или словаря).
- Кража локального API-ключа OpenRouter после ограниченного действия пользователя.
- Повреждение структуры State или IndexedDB при обработке специально сформированного файла импорта.
- Обход проверки целостности учебного пакета (course package).

### Medium (Средний уровень)

- Reflected HTML injection без возможности выполнения произвольного JavaScript.
- Ограниченная утечка нечувствительных диагностических метаданных.
- Небезопасное открытие внешнего URL с явным кликом пользователя (отсутствие `rel="noopener noreferrer"` или обход схемы).

### Low (Низкий уровень)

- Отсутствие отдельных рекомендуемых заголовков безопасности (Security Headers) на статическом хостинге.
- Раскрытие технической информации некритичного характера (версии сборки, тайминги).
- Общие рекомендации по hardening без прямого вектора эксплуатации.
